---
title: "Onboarding API"
description: "Opening a space, running KYB or KYC, reading the document checklist, and watching verification status."
---

Onboarding turns a signed-in user into a space that can hold money. Two paths exist and they differ only in who is verified.

## Spaces

```text
GET  /me                       → the user, their spaces, and the active one
POST /me/active-organization   → switch the active space
POST /me/personal-space        → open the caller's personal space
```

Opening a personal space is idempotent: a caller who already owns one receives it rather than a second. Opening does not switch you into it — switch explicitly.

## Company verification (KYB)

```text
GET  /kyb/doc-list   → documents required for the country of registration
POST /kyb/start      → open the verification and get a hosted link
GET  /kyb/status     → current state
```

`kyb/start` refuses a country the platform does not serve: there is no verification profile to run, so the request fails rather than opening something that could never complete.

## Personal verification (KYC)

```text
POST /kyc/start    → open the verification for the space owner
GET  /kyc/status   → current state
```

`kyc/start` takes the owner's **stated country of residence**. It selects the verification profile, is recorded as given, and is never inferred from network location. Replaying the call returns the existing verification with a fresh hosted link rather than opening a second one.

Both calls refuse any country outside the United States and Canada.

## Verification is asynchronous

Neither call returns a decision. They open a filing and hand back a link to the hosted flow. The outcome arrives later from the provider, and status endpoints reflect it when it lands.

<Note>
  There is no automatic approval path. Do not build a flow that assumes a positive outcome, and do not poll faster than your users can act — subscribe to the status your dashboard shows.
</Note>

## Onboarding progress

Progress is stored per step so a user can leave and come back. The current step is readable, and the flow advances as each step completes.

## After verification passes

The payment account is provisioned automatically. Depending on the provider, a hosted agreement may need accepting before money movement opens. Read the payment account status rather than assuming provisioning finished the moment verification did.

## Legal agreements

```text
GET  /manifest             → current document set and version
POST /acceptance-intents   → begin an acceptance
POST /acceptances          → record it
```

Acceptance is recorded against immutable document versions. If the set is republished between the intent and the acceptance, the acceptance is refused and the user must act on the current versions.

Whether an unaccepted document set restricts access is an environment decision, so do not build a client that assumes acceptance gates a request. Read the status and render it; let the API decide what to refuse.
