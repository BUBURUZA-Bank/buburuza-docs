# API Overview

The Buburuza API is a JSON REST API under `/api/v1`. It covers authentication, organisation onboarding, accounts & wallets, and money movement — the same operations available in the dashboard.

## Base URL

```
https://app.buburuza.io/api/v1
```

The authoritative OpenAPI 3.x specification is available as a machine-readable contract; see [SDKs & Libraries](/api/sdks-and-libraries).

## Routing

| Prefix | Area |
| --- | --- |
| `/api/v1/auth/*` | Authentication: signup, login, sessions, MFA, passkeys |
| `/api/v1/app/*` | Application: onboarding, accounts, wallets, transfers, transactions |

## Conventions

- **JSON**, field names in `snake_case`.
- Every successful response is HTTP `200` with an envelope: `{ "data": <payload>, "correlation_id": "<uuid>" }`.
- Every request may carry `X-Correlation-Id`; the server always returns a `correlation_id` in the body.

### Example

```json
{
  "data": {
    "user_id": "usr_01h…",
    "first_name": "Jane"
  },
  "correlation_id": "4d3f9c1a-…-8f2b"
}
```

## Errors

### Validation errors — HTTP 422

```json
{
  "type": "ValidationError",
  "error": {
    "amount": [
      { "code": "greater_than", "message": "must be greater than 0", "data": null }
    ]
  },
  "non_field_errors": []
}
```

Field-level errors are objects keyed by field name; `non_field_errors` carries form-level problems.

### Other errors — 401 / 403 / 404 / 409 / 500

```json
{
  "type": "PermissionDenied",
  "error": { "code": "account_not_active", "message": "…", "data": null }
}
```

A single `error` object with `code`, `message`, and `data`.

## Idempotency

Mutating endpoints where retries are dangerous accept an `Idempotency-Key` header. Repeating a request with the same key does not duplicate the operation.

## Authentication modes

| Mode | Used for | How |
| --- | --- | --- |
| None | Starting signup (`POST /auth/sign-up/email`) | — |
| Registration | Signup steps after email confirmation (passkey, TOTP) | `X-Registration-Token` header |
| Access | All authenticated app endpoints | `Authorization: Bearer <access_token>` |
| MFA step-up | Completing login when MFA is required | `mfa_token` in the request body |

Access tokens are **short-lived**; refresh happens through an HttpOnly cookie on the auth service. Browser and mobile clients get this automatically.

## Correlation & tracing

Pass `X-Correlation-Id` on requests to tie client logs to server logs; the response body echoes the same identifier.
