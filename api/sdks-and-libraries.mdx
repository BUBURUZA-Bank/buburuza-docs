There is no hand-written Buburuza SDK. The platform publishes an **OpenAPI 3.x** document, and the supported path is to generate a client from it in your own language.

<Note>
  The specification is the authoritative contract. Where this documentation and the specification disagree, the specification is right — it is produced from the running service.
</Note>

## Generating a client

Point any OpenAPI generator at the published document. For example:

```bash
npx openapi-typescript ./buburuza-openapi.json -o ./src/buburuza.d.ts
```

```bash
openapi-generator-cli generate \
  -i ./buburuza-openapi.json \
  -g python \
  -o ./buburuza-client
```

Generate into a build step and commit the output, so a specification change shows up as a reviewable diff rather than a silent behaviour change.

## What a client must handle

Whatever you generate, four things need handling by hand:

<AccordionGroup>
  <Accordion title="The response envelope" icon="box">
    Successful responses wrap the resource: `{ "data": ..., "correlation_id": ... }`. Unwrap once in your client rather than at every call site, and keep `correlation_id` in your logs.
  </Accordion>
  <Accordion title="Decimal amounts" icon="calculator">
    Money is a decimal string. Generators often map it to a float or a plain string — map it to your language's decimal type before it reaches business logic.
  </Accordion>
  <Accordion title="An open error set" icon="triangle-exclamation">
    Branch on `code`, never on `message`. Some codes come from the payment provider unchanged, so the set is not closed. Always have a default branch.
  </Accordion>
  <Accordion title="Token refresh" icon="key">
    Access tokens are short-lived. Refresh before a call rather than waiting for a `401`, and never place a token in browser storage that scripts can read.
  </Accordion>
</AccordionGroup>

## Pinning

Pin the specification version your client was generated from, and regenerate deliberately. The API is versioned at `/api/v1`; within a version, additive change is expected, so a client that ignores unknown fields ages better than one that rejects them.
