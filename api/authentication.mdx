title: "Authentication API"
description: "How a session is created and refreshed: email codes, passkeys, TOTP, recovery codes, step-up, and session management."
---

Authentication is handled by the identity service. There is no password anywhere in the model: a session is established with an email one-time code and a phishing-resistant credential.

## The model

| Piece | Role |
| --- | --- |
| **Email one-time code** | Proves control of the address, at signup and on a new device |
| **Passkey (WebAuthn)** | The primary credential. Bound to the origin, so it cannot be phished or replayed |
| **TOTP** | The fallback credential where passkeys are unavailable, and the optional extra step |
| **Recovery code** | Single-use, issued once. The only route back with no other credential |

## Signup

```text
POST /email                 → send the confirmation code
POST /email/resend          → send it again
POST /email/confirmation    → confirm the address
```

After confirmation, enroll a credential before the account can be used.

## Enrolling a passkey

```text
POST /passkeys/enroll/options   → challenge and parameters for the authenticator
POST /passkeys/enroll/verify    → submit the authenticator's response
GET  /passkeys                  → list enrolled passkeys
DELETE /passkeys/{id}           → remove one
```

Enroll a second passkey on another device before removing the first. An account with one passkey and lost recovery codes cannot be recovered.

## Enrolling TOTP

```text
POST /mfa/enroll                  → begin enrollment
POST /mfa/confirm                 → confirm with a generated code
POST /mfa/recovery-code           → issue recovery codes
POST /mfa/recovery-code/confirm   → acknowledge that they were stored
```

<Warning>
  Recovery codes are shown once. Never log them, never write them to disk on the server, and never send them through support channels.
</Warning>

## Signing in

```text
GET  /login/options                → which methods this account can use
POST /login/email                  → request an email code
POST /login/email/confirmation     → submit the email code
POST /login/verify                 → complete a passkey assertion
POST /login/mfa                    → submit a TOTP code
POST /login/mfa/recovery-code      → spend a recovery code
POST /logout                       → end the session
```

## Step-up

Sensitive actions re-confirm identity inside a live session:

```text
POST /passkeys/step-up/options   → challenge
POST /passkeys/step-up           → assertion
```

A satisfied step-up authorises that action, not the rest of the session.

## Sessions

Sessions can be listed and revoked individually or all at once. Revoking everywhere ends the current session too, so expect the next call to return `401` and re-authenticate.

## Tokens

Access tokens are short-lived and refreshed while the session is live. Verify them against the published JWKS:

```text
GET /.well-known/jwks.json
```

Do not hard-code a signing key — keys rotate, and the JWKS is the source of truth.

<Warning>
  Store tokens in server-side storage, or in an http-only cookie set by your backend. Do not put a token that can move money into `localStorage`: any script on the page can read it, so one XSS flaw is enough to lose it.
</Warning>

## Your identity

```text
GET   /me            → the signed-in user
PATCH /me/profile    → update profile fields
```
