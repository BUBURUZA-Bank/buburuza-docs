All paths below sit under `/api/v1/app`. Every outbound payment is priced before it is created.

## Payout rails

```text
GET  /payout-rails                      → every rail with this space's standing
POST /payout-rails/{rail}/approval      → request approval for a rail
POST /payout-rails/{rail}/documents     → attach evidence a rail requires
```

The rails offered today are `ach` and `wire`; further rails are enabled per environment. Read the list from this endpoint rather than hard-coding it — each rail is reported with whether the environment offers it and whether the provider has endorsed this space for it. A rail the environment does not offer is refused with `rail_not_enabled`, and asking for it never spends a provider call. A rail can be reported available on an endorsement that has not been read back yet — treat that as "not refused", not as "confirmed working".

## Fee previews

```text
GET /transfers/fee-preview      → price a transfer
GET /withdrawals/fee-preview    → price a withdrawal
```

Both return a quote:

| Field | Meaning |
| --- | --- |
| `fee_quote_id` | Cite this when creating the payment |
| net amount | What the recipient receives |
| fee | Charged on top |
| total debited | Net plus fee — what leaves your wallet |

Net plus fee always equals the total debited; the API rejects its own response if that does not hold, so you can rely on it.

<Warning>
  A quote is **single-use** and expires **ten minutes** after issue. A consumed, lapsed, mismatched, or unknown quote all fail as `quote_expired`. Recover by pricing again — never by retrying the same identifier.
</Warning>

The fee is priced per payment from destination and risk, so there is no fixed percentage to hard-code. Show the preview to your users as the price.

## Transfers

```text
POST /transfers                → create, citing a fee_quote_id
GET  /transfers/{transfer_id}  → status
```

## Withdrawals

```text
POST /withdrawals                    → create, citing a fee_quote_id
GET  /withdrawals                    → list
GET  /withdrawals/{withdrawal_id}    → status
```

A withdrawal pays an external recipient. Create the recipient first — see [Recipients and beneficiaries](/api/recipients-beneficiaries).

## Payment intents

```text
GET  /payment-intents                            → list
GET  /payment-intents/{payment_intent_id}        → one intent
POST /payment-intents/{payment_intent_id}/resolve → resolve one that needs a decision
```

An intent that stalls waiting on information surfaces here rather than failing silently.

## Transactions

```text
GET /transactions                                  → filter by account, wallet, kind, status
GET /transactions/{transaction_id}                 → one transaction
POST /transactions/{transaction_id}/recipient      → attach a recipient after the fact
```

Every money event lands here — funding, transfers, payouts, and fees, each as its own entry with its own kind. A payment and its fee are separate rows, so your ledger reconciles without inferring anything.

## Rates

```text
GET /rates   → current exchange rates
```

Read-only. Use it to display conversions rather than integrating a separate rate source.
